## Как перенести поиск

Достаточно самостоятельной обычной Slurm-задачи в `main`/`normal`: первоначально **4 CPU, 8 GiB RAM, time limit 24 часа**, batch size 100, четыре download workers. Это стартовый запрос, основанный на локальном пилоте и нынешнем коде с четырьмя HMMER workers, а не новый измеренный cluster benchmark. Большая часть локальной оценки времени приходится на получение протеомов; дополнительные CPU не гарантируют ускорения.

1. Разместить проект отдельно от GAPH, например `${MO_WORKDIR}/lariocidin`. Не использовать/менять его `work/`, caches, окружения, Slurm launchers или уже полученные результаты. Крупные протеомы, `.env` и временные batch FASTA должны лежать на shared scratch, а не в home.
2. Собрать отдельное Linux x86_64 окружение по portable `environment.yml`; macOS `.env` и `environment.osx-arm64.lock` переносить нельзя. На `sphinx` Python 3.10.12, отсутствуют Biopython/pandas и системные HMMER/BLAST. Существующий Micromamba доступен, но GAPH environments не изменять. Совместимость точных package pins на Linux ещё не проверена.
3. Передать небольшой зафиксированный пакет: два scripts `screen_diversity_proteomes.py`/`profile_search.py`, обе source selection TSV, две versioned family HMM и manifest/checksums. Остальные общие данные/скрипты нужны для последующей контекстной курации и расширенного сравнения, а не для первого protein-screen. Перенос не выполнялся.
4. Выполнить 12 + 12 genome pilot **через Slurm**, проверить outbound HTTPS с compute node, версии/контроли, время, RSS и фактический диск. Историческая доступность интернета в compute nodes не является сегодняшней проверкой. На `sphinx` не запускать HMM/BLAST/полный поиск.
5. После пилота — тот же основной protein-screen по зафиксированным 41 687 source-записям, затем адресный контекст и согласование aliases. Это 41 687 записей до трёх известных cross-source GCA-base перекрытий, не уже доказанное число независимых геномов. Для точных input файлов оставить запас сверх локальной оценки 39,9 GiB; нынешний filesystem-free guard не заменяет персональную квоту. Ошибка quota/write должна остановить получение данных, не превращаться в биологическую недетекцию.

Кластер выглядит пригодным для выбранного объёма; проверка Linux environment, compute-node сети и персонального доступного диска остаётся частью подготовки. Успех/скорость cluster pilot пока не заявлены. Основной научный endpoint (обоснованные BGC с отдельным неопределённым слоем или все C-гомологи) всё ещё требует обсуждения по [отчёту 12.10](2026-10-12-diversity-redesign.md); пользовательский ответ сейчас относится к месту исполнения. HGT-протокол не меняется.
